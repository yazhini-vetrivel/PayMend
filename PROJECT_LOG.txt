# Day 1 — Payment Failure → Root Cause → Recovery Agent

*Buildathon project: an AI agent that monitors Razorpay for failed
payments, analyzes their reasons, and (eventually) recovers them.*

This was the day of the foundations: a GitHub repo, a database, an
ingestion layer, and the first step towards intelligence — a rule-based
classifier that takes the raw Razorpay error code and outputs the business
level reason for the failure. That's what got done, what went wrong and how
my initial plan differed from what really happened.

## What got done

- Project repository created
- Razorpay test-mode API keys generated and added to the config
- `RazorpayClient` wrapper built (Orders + Payments API)
- SQLite database initialized via SQLAlchemy
- Basic ingestion layer with polling mechanism
- Failure detection (extracting payments waiting for recovery)
- Rule-based root-cause classifier
- Failed-payment synthetic data generator
- Labeled data generator for the classifier testing purposes

## Problems faced (and how I got past them)

**1. Could not access the API keys within `razorpay_client.py` module.**
The fix was to import `os` and point the module directly at the `.env` file
— the client did not recognize the environment variables otherwise.

**2. Had to initialize the old DB file when implementing the failure
detection.** The addition of the failure-detection query involved a
schema change, which meant dropping and initializing the old SQLite file
once again. Not a big deal, but one to remember: every schema change means
a new `python -m app.db` (or migrations, eventually).

**3. Webhooks were more than I needed.** My original plan involved
implementing webhook-based ingestion, but creating a publicly accessible
endpoint plus its signature verification was quite an effort for what I
could achieve with polling. So, switched to polling — easier to
demonstrate and equally valid way of proving my recovery logic.

**4. Data generation code kept failing when executed from the terminal.**
Instead of continuing to fight with the environment in the terminal, I
moved the equivalent of this code to a Jupyter Notebook cell and executed
it there — it worked as expected.

**5. Tried to train the ML classifier, but ran into a problem I couldn't
solve yet.** This will be my first task for tomorrow.

# Day 2 — Payment Failure → Root Cause → Recovery Agent

*Buildathon project: an AI agent that watches Razorpay for failed payments, diagnoses why they failed, and recovers them.*

Today started with a broken ML classifier training and the goal to get that fixed while also putting together a policy engine and integrating everything. ML turned out to be harder than expected, so I decided to push the debugging aside and just finish what depended on the rule-based classifier anyway — it works standalone already, anyway, and that's what the recovery flow actually requires. Today the agent went from "classifies a failure" to "classifies, decides, acts, and explains itself".

## What got done

- Policy engine (`app/policy.py`) — maps each root cause to an action: retry with backoff, notify, or escalate, every rule bounded by a hard retry cap
- Recovery executor (`app/recovery.py`) — the full closed loop: fetch → classify → decide → execute → record → log, for one payment at a time
- Batch runner + metrics script (`scripts/run_recovery_batch.py`) — runs the agent over every pending failed payment across multiple rounds and prints/saves a recovery-rate report
- Deliberately went looking for real bugs (rather than stumbling on them) and found two, plus verified one thing that could easily have been a bug but isn't
- Wrote up `ARCHITECTURE.md`, `README.md`, and `DEBUGGING.md`

## Problems faced (and how I got past them)

**1. Retries that never actually got retried.** The batch runner should show fewer payments processed each round as retries resolve. It didn't — round sizes stayed the same instead of shrinking. One conditional fix later, round sizes converged perfectly: 70 → 19 → 0.

#Day 3

**Symptom:**
End-to-end batch run showed 0.0% recovered for `expired_card`, `invalid_card`,
`insufficient_funds`, and `risk_block`, while `timeout` (100%) and `auth_failure`
(66.2%) recovered normally.

**Root Cause:**
Not a bug in retry logic — the recovery metric only measured outcomes from the
immediate batch pass. `policy.py` correctly routes these four root causes to
`NOTIFY` or `ESCALATE` instead of `RETRY`, because retrying with the same
expired/invalid card, or auto-retrying a risk-blocked payment, cannot succeed
and can actively hurt merchant standing. But nothing in `recovery.py` modeled
what happens *after* a NOTIFY action — i.e., the customer updating their card,
topping up their balance, or completing 3DS later — so those payments looked
permanently unrecovered even though the correct action had been taken.

**Fix:**
- Added `FOLLOWUP_SIMULATION_PROBABILITY` in `policy.py` — bounded, per-root-cause
  probabilities modeling customer follow-through after a NOTIFY (e.g. updating
  an expired card, topping up funds).
- Added `process_followups()` in `recovery.py`, run after the main
  `run_recovery_batch()` pass, which simulates follow-through for every payment
  whose last action was NOTIFY and updates `Payment.recovered_amount` /
  `is_recovered` accordingly.
- **`risk_block` was intentionally left out of `FOLLOWUP_SIMULATION_PROBABILITY`.**
  It has no simulated follow-up path and will correctly stay at 0% recovered
  indefinitely — recovery there requires a human clearing the fraud flag, not an
  automated action. This is a guardrail, not a defect.

**Files changed:** `app/policy.py`, `app/recovery.py`

**Verification:** Re-ran `scripts/run_recovery_batch.py` end-to-end. `expired_card`,
`invalid_card`, and `insufficient_funds` now show partial recovery via simulated
follow-through; `risk_block` remains 0% as expected.
